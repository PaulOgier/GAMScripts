Offboarding Command Builder

Build a valid python3 offboard_user.py command without reading the source. Cross-platform — open this file in any browser.

Dry-run is the default. The script makes no changes unless you select Execute mode (which adds --doit). The Copy button stays disabled until the command is valid.
Containment always runs (v5.2.0). In Execute mode there is no combination of options that skips it. Even --backup-drive --no-transfer --no-suspend, which reads like a precautionary backup, still moves the user to the offboarding OU, wipes their recovery email and phone, revokes app passwords and OAuth tokens, signs out every session, scrambles the password and hides them from the directory. That is deliberate — the tool exists so a leaver cannot take data with them mid-migration — but it is irreversible, so choose Execute mode on purpose. The plan the script prints before acting says the same thing.
Shared Drives are reported, never moved. Their content belongs to the drive, not to a member, so nothing here backs it up or transfers it. Since v5.2.0 the script lists every Shared Drive the leaver organises and flags any where they are the ONLY organiser — delete that account and no member can add members, change settings or delete the drive again, and recovering it means a super admin taking it over from the Admin console. Add a replacement organiser before you delete anyone.

1. User to offboard

The full Google Workspace email of the account being offboarded. Check the spelling carefully — most operations can't be undone once the script runs.

2. Execution mode

⚠ Scorched earth — permanent deletion

This permanently DELETES the user after killing access, removing groups/licences, and suspending. The script refuses any backup or transfer flag alongside it (run those first, then delete), so those sections are disabled here. The read-only pre-flight snapshot still runs.

The script requires --doit and --force (added automatically) and a typed-email confirmation at runtime. This builder also requires you to re-type the email below.

4. Transfer destinations

Where Drive files, emails, aliases, and calendar access go when no per-phase override is set. Usually the departing user's manager. Leave blank only if you're setting individual destinations for every active phase. v5.2.0 pre-flight: the script refuses a destination that is the leaver themselves, including one of their own aliases — transferring to self does nothing and forwarding to self is a mail loop. It also refuses a SUSPENDED destination, because a restore into one fails with a generic backendError that reads exactly like rate limiting and can burn hours before it gives up. Both checks run before anything destructive, so a typo cannot half-offboard someone.
Override the Drive destination. Useful if legal or IT should receive the files rather than the manager.
Override the email migration destination. Requires GYB configured on both source and destination accounts.
Override the alias destination. The receiving account must be in the same Google Workspace domain as the alias being transferred.
Override the calendar access destination. This shares the calendar — it does not transfer ownership.
Set up Gmail forwarding to this address. Can be a group. Only catches new mail — messages that arrived while the account was suspended are not forwarded retroactively.
Sends a summary notice to this address after the script finishes. Can be a group or the manager. Leave blank to skip the end-of-run email.

8. Advanced
Where the script writes its log file. Defaults to ./logs relative to where the script is run. Use an absolute path if you run the script from different directories to avoid logs scattering across your filesystem.
Where snapshots, mailbox backups and Drive backups are written. A mailbox backup can reach hundreds of gigabytes, so point this at a local disk and never inside iCloud, OneDrive, Dropbox or Google Drive — a synced folder will try to upload all of it. Since v5.4.0 a re-run that finds an earlier mailbox backup here offers to resume into it instead of re-downloading (under --force it resumes automatically when the folder is 30 days old or less); since v5.5.0 Drive backups resume the same way, and the mailbox size is checked against free disk space before the download starts.
GYB rejects anything outside 1–100 outright, and it does so only when the restore starts — after the mailbox has already been downloaded, which on a large mailbox is hours. Since v5.2.0 the script checks the value when you launch it instead. Messages sent per request when restoring mail. Measured on a real mailbox: 1 gives ~1,200 msg/hr, 10 gives ~5,800, 100 gives ~9,100. GYB rejects anything above 100. The script steps this down automatically (100 → 75 → 50 → 25 → 10) if Gmail starts throttling, so the default is a safe starting point.
Restore-only mode: restores from a backup you already have and skips the download and every other phase. Use it to finish a restore that died part way. Re-running is safe — Gmail discards messages it already holds, so nothing is duplicated. Needs --force.

9. Profiles — saved in your browser only

Profiles store your current settings by name in browser localStorage — nothing is sent anywhere. Useful if you regularly offboard to the same destinations. Profiles are browser-specific and won't carry over to a different browser or machine.
